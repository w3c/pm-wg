w3c/epub-specs#3071

wendyreid: this is "offer a human readable way to identify the annotation"
… we talked about this a few weeks ago, about providing breadcrumbs and hierarchy to find the target of the annotation

LaurentM: proposed adding two new pieces of metadata to help people find the target

LaurentM: we have two solutions there, as strings, one which will be different from one rs to another
… the second one will be more structured and is a little harder to define. Should it be a page? or a locator?
… I recommend we keep a single label and let the reading system make the magic

Hadrien: What is this for? If we're talking about display in an RS, it probably isn't needed. The main use would be when you don't have access to the book
… in that case, some kind of label which may not always be useful, progression in the book might be the best we can do. I don't recommend using page or page list because they are not reliable

wendyreid: I agree progression is challenging, and page list isn't reliable. I know there are a lot of books without page lists and this is a challenge. Maybe percentage plus the headings would be sufficient
… in the context of a reading system it might not be needed, but when it is exported to another tool, or the exported results themselves, when you look at annotations as an export, you need context to know what you are looking at. It's not adequate to see just the note

duga: I understand why we might want these, page in the current proposal is only for fixed layout, which might be not annotated very often. We should figure out an answer, we might not want to create new strings. We have had problems with strings in the package before by allowing raw strings with no markup. Internationalization will make this more
… complex. If we're starting to introduce new strings that will be displayed with no markup, it may not be properly represented

Hadrien: I hear you Brady, I feel like there is not much we can do about this. Whenever we try to use HTML it is useless, and usually converted back to a string. We need to find a way to do this with unicode but that isn't our problem to solve. We keep going back to this, but I think it is a unicode problem and not ours.

wendyreid: where does that leave us?

duga: we put this on the agenda because it didn't get much traction. And that is happening here. Do we have someone who really champions this? Is it really needed?

LaurentLM: As we have seen I think this feature ins't about the interchange between reading systems, more about exporting them to something that is human readable. We know that human readable export from a reading system may be something like HTML and used for things like citations.
… since we have decided not to conflate annotations with citations maybe we don't need this

wendyreid: Just exporting annotations essential raw, and import it into HTML or Markdown, all I will get is which book its attached to, a locator that isn't human readable, and I'll know if it is a highlight or a note. That is not enough to be usable. We see that in how platforms current export annotations. We need at least some human readable
… parts. Kobo mentions the chapter and that gives me a chance to find the target

Hadrien: This has to do with whether you can present this outside a reading system or not? Do we want the format to be merely interchange or do we want it to be useful outside RS? Laurent: When we started designing the export mechanism, I pictured it as a source for creating a human readable output in PDF or HTML. I realize that the reading system is capable of doing this. Kobo has multiple file formats on export, including ones that are human readable. We could leave this to the reading system to decide.

wendyreid: Hadrien has asked an important question. What is the primary use case we are targeting. They are not mutually exclusive, but what are we leaning into more? We want a usable format, there has been a request for this for a long time. What are their goals? Exporting or interoperability?

sueneu: I worry a little about leaving export to reading systems, if our goal is interchangability, reading systems might be tempted not to export things in a human readable way

duga: the suggestion isn't to leave it up to the reading system, but to leave the options up to the user. You can choose HTML, PDF or something like .annotation(machine readable)

If we want a human readable format, we need to go back to basics. We need a clear separation between human and machine readable

LaurentLM: We guarantee that with our format that you can transfer your annotations from one RS to another as long as you have the same book in each.
