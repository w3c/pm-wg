Full Bleed Images

wendyreid: we have one open issue with full bleed images, and the primary use case is light novels, but its similar to mixed formats, covers, some books are using fixed layout intead

shiestyle: the situation in Japan is partially fixed layout indicated in the spine. Best practice is no CSS on fixed layout, since that always means one image per page in the spine.
… this topic should be discussed globally.

Hadrien: almost every reflowable epub needs this, at least for the cover
… today comic creators put an image into an HTML file, and then in a reflowable system. They inject styles, margins, multi columns. Which can have a negative impact on how the content is displayed.
… some reading systems don't have the ability to show a full page image and this leads to a bad experience. This can be an accessibility issue if an image can't be zoomed into.
… there are a lot of reasons to do this. The Japanese approach is rooted in 3.0.1. The problem is that most RS have different rendering systems for FL and Reflow. That's why we see little adoption outside Japan. In a reflow EPUB, the user has options like fonts and columns. The options for fixed layout can be completely different. From a UX

perspective this opens a lot of questions.
… it is both a technical issue and a UX issue. This is why it is not used outside of Japan
… layout overrides goes well beyond this issue. With those, we could have fixed layout that are not images. So it might be overkill. Perhaps we could solve this problem without going nuclear.

wendyreid: I agree, and as long as the cover is identified most reading systems will attempt to display it as fixed. I've notice that most fixed layout readers depend on the viewport dimensions not changing. It might be shrinking or cropping.

sueneu: depending on the kind of book, all the images could be a different size. We need to make it clear that you can't rely on a standard viewport.
… there is no where in the spec that requires the same viewport on every page of an FL

Hadrien: the viewport problem will be discussed in the Manga group. There are many extensions for providing the viewport. It is not uncommon for comics to have multiple viewports. It makes it harder for some systems to show a full spread. And this is one of the problems about relying on fxl. What do we need to give reading systems for this?
… so they know when something is an image, and which image it is, and then they are more likely to get something out of it that is effective

sueneu: My customers do make books of poetry, it's very important that the poetry be displayed with the line breaks etc

Hadrien: most of the editors find reflow for poetry unacceptable, I do FXL, but sometimes they demand images even
… I want to see that addressed somehow

duga: there are two usecases with full bleed, here's the cover, here's a full bleed image inside reflowable text. Are we going to tackle both of these? Are we going to figure out how to identify a full bleed image in the spine.

wendyreid: we've had discussions about RS ability to convert FXL to reflowable so it can be customized, but we can still see the original image/styling.

sueneu: spine structure could get very strange with a full bleed image within a Reflowable

Hadrien: we have full bleed images, but maybe relying on the viewport we could find another way, like using just height. We could rethink how we fit things in general. Fitting isn't always the right option

Samuel: yesterday we talked about comic accessiblity via audio, but there are other use cases like dyslexia, that can interfere with the author's artistic expression.
